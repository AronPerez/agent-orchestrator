# scripts/

Source of truth for the local launchd service wrappers. These are **deployed by
copy** to `~/.ao/` — launchd runs the copies, not this checkout. After editing a
script here, re-copy and restart the job (see below).

## Fresh machine

Everything below is reproducible from this repo with one command:

```sh
scripts/dev-setup.sh   # build ao, deploy scripts, generate plists, load jobs
```

Idempotent; never restarts an already-loaded job. Prereqs it checks but does
not install: go, node (nvm), tmux, claude, `cd frontend && npm install`.
Full path — prereqs, project registration, verification, pitfalls:
[`skills/machine-setup/SKILL.md`](../skills/machine-setup/SKILL.md).

| File                     | What it is                                                                                                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dev-setup.sh`           | one-shot machine setup: builds + deploys all of the below, generates the plists, loads the jobs                                                                                   |
| `mobile-web-server.sh`   | launchd wrapper for the mobile FE — Expo/Metro on the LAN at `:8081` (serves `packages/mobile`)                                                                                   |
| `ao-svc`                 | `up/down/status` for the env + `mobile-web` jobs; `reload` rebuilds the `ao` CLI and refreshes `~/.ao/bin/ao`                                                                     |
| `daemon-build.sh`        | builds `ao` from `backend/` and installs it on PATH (`~/.local/bin/ao` → `~/.cache/aoagents/.../ao`)                                                                              |
| `install-desktop-app.sh` | build + install the desktop Electron app locally (macOS): `npm run make`, ao CLI rebuild, deep ad-hoc re-sign (fixes launchd error 162 on unsigned builds), de-quarantine, launch |
| `bootstrap-fork-host.sh` | one command on a fresh Debian/Ubuntu x64 or arm64 host: builds this fork's daemon from `--ref` (default `develop`) and installs it as a systemd user service through upstream's `setup-self-hosted.sh`; re-run to upgrade; `ssh -t user@box 'bash -s -- --lan' < scripts/bootstrap-fork-host.sh` runs it from your laptop. Its test: `bash scripts/bootstrap-fork-host.test.sh {default|lan-ref|bundle|unsupported}` |

The plists at `~/Library/LaunchAgents/dev.agent-orchestrator.{env,mobile-web}.plist`
are **generated by `dev-setup.sh`** — edit the heredocs there, not the installed files.

**The browser UI is not a service any more.** `lan-web` (a Vite renderer on
`:3000`) and `phone-bridge` (`ao-phone-proxy`, which laundered `Origin` headers
so a browser could reach the loopback daemon) were retired once the daemon began
serving the web UI from its own LAN origin. Enable Settings → Connect Mobile and
open the host:port it shows. `dev-setup.sh` boots out both jobs and deletes their
plists on its next run. This needs a daemon built at or after `2399595db` — an
older one answers a browser navigation with a JSON 401.

**One daemon binary: `~/.ao/host/current/resources/daemon/ao`.**
`install-desktop-app.sh` installs it from the freshly built app
(`setup-self-hosted.sh --app`), which also points `~/.ao/bin/ao` and
`~/.local/bin/ao` at it. The `dev.aoagents.self-hosted` LaunchAgent starts it at
login only (no KeepAlive). The desktop app replaces any daemon it did not start
(per-launch browser-runtime token), so the one-shot `dev.agent-orchestrator.env`
job sets `AO_DAEMON_COMMAND` to that same binary, plus `AO_KEEP_DAEMON=1` so
app-spawned daemons survive app quit. Never give a daemon job KeepAlive: once
the app takes over it would respawn into "daemon already running" forever.

## Deploy after editing a script

```sh
cp -f scripts/{ao-svc,mobile-web-server.sh} ~/.ao/
launchctl kickstart -k "gui/$(id -u)/dev.agent-orchestrator.mobile-web"   # if mobile-web changed
```

## Deploy a new ao CLI (`~/.ao/bin/ao`)

Worker sessions run `~/.ao/bin/ao` (their PATH pins `~/.ao/bin` first), a
**separate copy** from the PATH install. Install it **atomically** (`.new` +
`mv`) — a plain `cp -f` over a _running_ binary corrupts its code signature and
macOS SIGKILLs it (`OS_REASON_CODESIGNING`). `ao-svc reload` does this for you.

The daemon itself is bundled inside the desktop app — to deploy a new daemon,
run `install-desktop-app.sh` (below). Live agents keep their old argv across a
daemon replace; to pick up new flags/config, cycle each session:
`ao session kill <id> && ao session restore <id>`.

## Install the desktop app locally

A local `npm run make` produces an **ad-hoc-signed** app (no Apple Developer
ID). macOS auto-update refuses it (its signature can't satisfy the installed
app's code requirement), and the default electron-forge ad-hoc signature is
often broken for a customized bundle, so `open` fails with launchd error 162.
`install-desktop-app.sh` does the manual dance instead:

```sh
scripts/install-desktop-app.sh                 # build + install + launch (spawns its bundled daemon)
scripts/install-desktop-app.sh --skip-build    # reinstall an existing build; --help for all flags
```

The app and its bundled daemon come from the same `npm run make`, so they always
match. Don't mutate the tree mid-run: a running daemon with a _different_
`buildIdentity` (git revision + `-dirty`, reported in `/healthz`) surfaces as a
"different build" error instead of a clean takeover. The script also rebuilds
the `ao` CLI to the same commit unless `--no-daemon`.

**Update feed.** `forge.config.ts` bakes the GitHub repo the app's updater
polls from `AO_RELEASE_REPO`, defaulting to upstream — so a plain
`npm run make` builds a fork app that checks **upstream's** releases. The script
sets `AO_RELEASE_REPO` from this checkout's `origin` remote (an explicit
`AO_RELEASE_REPO=owner/repo` wins; `--print-release-repo` shows what it will
bake). This fork publishes no releases, so the updater stays quiet instead of
offering upstream's app.

**Updating the client on another Mac.** There is no release channel; rebuild
from source there (it needs Go, Node and the Xcode CLT):

```sh
ssh -t user@othermac 'cd ~/dev/agent-orchestrator && git pull --ff-only && scripts/install-desktop-app.sh'
```

It quits the running app, installs, re-signs, and launches in that Mac's GUI
session. A Mac that is only a browser client needs nothing — the host's daemon
serves the UI.

Full runbook (403 mux gotcha, TCC/Desktop override, session-restore behavior):
`~/.ao/FEREADME.md`. Agent-facing guide: `skills/local-services/SKILL.md`.

`running.json` is daemon run-state (`~/.ao/running.json`), regenerated every
start — gitignored here; never commit a stray copy.
